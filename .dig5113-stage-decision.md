**What the head does.** Five changes, all in the execution-workspace lifecycle.
1. The reaper archives a dead row. A new delivery state, `worktree_missing`, is derived from a recorded path that is gone, and the delivery gate admits it. Every other gate stays: terminal source tree, not dirty, the reopen fence, no live run, the advisory lifecycle lock, and the guarded archive UPDATE. Under the lock the archive re-verifies that the path is still missing, so a path that comes back is not archived.
2. The cooldown bypass is dead rows only. `cooldownCutoff` is null for a dead row and unchanged for a live row, and the loop check and the guarded statement read the same value, so they cannot disagree.
3. Cleanup of a dead row skips the HEAD comparison and the worktree cleanup lock, both of which read the dead path. Branch deletion is `git branch -d`, never forced. A refusal is a warning, `cleaned` stays true, and no `cleanup_failed` is written.
4. The finalize guard. A missing worktree no longer fails the run: the guard skips the branch-incoherence failure for the reason code `missing_worktree`, records the dead workspace in the operation log, and names `PATCH /api/execution-workspaces/{id}` with `{"status":"archived"}`. `reconcile-branch` is named nowhere and the test asserts that string is absent.
5. A sanctioned detached review read. Before anything moves: the tree is clean, the detached sha is named as `at <sha>` in the run's own issue title or body and is a prefix of HEAD, the recorded branch exists, it is not checked out in another worktree, and the sha is reachable from a remote ref. Then, and only then, `git checkout <recorded branch>` runs. It does not move the branch ref, does not force, does not delete a commit and does not rewrite `branchName`. A dirty tree at the named sha fails before the dirty-quarantine repair, which is the right order: that repair would move the seat's uncommitted work off the detached HEAD.
