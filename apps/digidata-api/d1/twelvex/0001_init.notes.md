## Review notes: status

1. **"26 tables" — correct, with a caveat.** 25 business tables plus the
   `schema_migrations` ledger. Stating it as 25 `fx_*` avoids the conflation.
2. **"69 indexes" — correct, and it counts two kinds.** 43 explicit + 26
   implicit. The draft is not missing 26 indexes.
3. **"9 CHECKs left as comments" — correct. All 9 are now real constraints.**
   `fx_bookkeeper_verdicts.timeframe`, `fx_digest_publish_attempts.outcome`,
   `fx_economic_calendar.impact`, `fx_idea_eval.{closed_by,grade_basis,horizon_days,outcome}`,
   `fx_macro_snapshot.frequency`, `fx_trade_ideas_snapshot.timeframe`.
   `pg_dump` emits a table `CHECK` as a comment immediately before the `CREATE TABLE`,
   and `X = ANY (ARRAY[...])` has no SQLite equivalent, so each is translated to
   `X IN (...)` with `IS NULL` preserved where the source allowed it. The source
   expression is kept as a comment above the constraint it produced.
4. **"23 jsonb->TEXT" — the draft records no source type per column, so this is
   reconciled rather than confirmed.** What is measurable is which columns carry a
   JSON default: exactly **20 columns carry `DEFAULT '[]'`**. PG's empty *array*
   literal is `'{}'`, so `'[]'` is evidence of `jsonb`, not of an array.
   Those 20 now carry `CHECK (col IS NULL OR json_valid(col))`.
   Three further JSON/array-shaped columns carry no default and are **left
   unguarded on purpose**: `fx_relevance_llm_cache.reviews`,
   `fx_idea_eval.target_prices`, `fx_market_snapshots.payload` (20 + 3 = 23). If a
   PG array ever reaches one of them it serialises as `{1.5,2.0}`, which
   `json_valid` rejects — a wrong guard there would break inserts rather than
   catch them. `reviews` and `target_prices` are the two array-named columns and
   are the likely members of the reviewer's "2 arrays->json".
5. **"1 GIN index TODO" — correct, and now a decision rather than a TODO.**
   `idx_fx_rh_v2_currency_views ON fx_research_history USING gin (currency_views)`.
   SQLite has no GIN, and `json_each()` is a table-valued function so a B-tree
   index is never consulted for it. The file carries a note recording the access
   pattern ("rows whose `currency_views` contains $1"), the equivalent query, and
   the three indexable options — a normalised side table (preferred), a stored
   comma-joined column, or FTS5 over a flattened copy — all of which are data
   changes and therefore gated on ticket 0 (Chris's snapshot). Nothing was
   dropped silently.
6. **"14 numeric->REAL (money precision)" — NOT VERIFIABLE, and open.** See below.

## Open item: money precision

The draft carries **53 `REAL` columns**, not 14, and records no source PG type
per column. There is no `pg_dump --schema-only` catalog and no generator on this
host (`~/Code/supabase-exit/tx.log` reads `dump rc=1 / FAILED`), so which of those
53 came from `numeric` is **not recoverable from the artefact**.

Blind-converting `REAL` to `TEXT` would break every reader, including the
TypeScript in PR #5404 — that would be a regression, not a fix. The fix is to make
the generator emit the source type per column so the mapping is auditable, then
decide per column. Left open deliberately; recorded rather than guessed.

## What the schema still does not carry

Unchanged from the draft's trailing block: triggers `null`, functions
`["fx_hub_has_access"]`, RLS policies `21 (-> Worker authz)`, views `null`. There
are no `FOREIGN KEY` clauses. SQLite ignores `PRAGMA foreign_keys` at
application time on a connection pool, so RLS/trigger parity belongs to the
Worker authorisation layer.

## Verifying

```
python3 scripts/verify_d1_twelvex_schema.py
```

It applies this schema to a fresh database, discovers every `CHECK` from the
applied schema, asserts each table accepts a conforming row, then asserts each
constraint **rejects** a violating row. A constraint that cannot fail is a silent
no-op, so the harness is only meaningful because it can fail: on the pre-review
draft it exits 1 with `expected 9 enum CHECKs, got 0`.

Requires the JSON1 extension. Verified on SQLite 3.51.0.

## Scope

Schema only. No data, no migration of any kind, no Cloudflare binding or deploy
change, no cutover. Supabase stays live and untouched as the rollback.
