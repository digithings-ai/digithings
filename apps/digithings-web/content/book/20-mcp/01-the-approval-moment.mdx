---
title: The approval moment
order: 1
summary: >-
  What happens when a tool needs a person, and why the person approves a
  recorded call rather than a description of one.
---

Some tools run unattended; some wait for a person. Which is which is the
operator's call, written on the row that adds the tool server: a list of the
tools the model may use, and a list of the ones that change something. A row
that lists allowed tools but names none as changing treats all of them as
changing, so forgetting the second list fails safe.

When the model asks for a tool that changes something, the hub does not run
it. It records the exact call, the tool and its arguments, under an opaque id,
and stops the turn. The chat shows the call and asks. The person's answer is a
separate request that carries only that id and a yes or a no, so nothing in
the answer can change what will run: the hub executes the call it recorded, or
nothing. The id is bound to the session that raised it, so it cannot be decided
from another conversation, and the gate is applied again at the moment of the
decision against the operator's current settings.

> is governed automation, not a demo. The operator decides what may run alone,
> and a person approves the call itself, not a summary of it.
