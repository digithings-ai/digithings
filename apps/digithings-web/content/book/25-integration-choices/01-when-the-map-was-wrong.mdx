title: When the map was wrong
order: 1
summary: >-
  The deployment reference once described the chat scaffold as removed and
  its platform tier as free. The tree says otherwise, and the reference now
  says so too.
---

The deployment reference disagreed with the system it described. It described
the chat's edge scaffold — worker plus
container — as removed on a past date, with no deploy path, on the grounds
that containers need a paid platform tier the project did not hold. Both
halves of that sentence had gone stale: the scaffold is live in the tree,
it serves real traffic on the main site, and the platform tier it needs is
the one the project holds.

```mermaid
flowchart LR
  DOC[reference says: removed, no deploy path] --> CHECK[measured against the tree]
  TREE[tree says: scaffold live, serving traffic] --> CHECK
  CHECK --> TICKET[a finding ticket]
  TICKET --> FIX[reference corrected, both halves]
  FIX --> BOOK[the record now matches the tree]
```

What the record says now: the chat edge scaffold is present and live, it requires the paid tier, and the chat surface ships
through two paths — the worker and container on the edge, and the chat
service on operator machines for the project's own use. Those are
different surfaces with different deploy paths, and the reference now
names both instead of describing one as gone.

Two things make this example worth keeping. First, it shows the review loop
working: the drift was found while preparing this material, it became a
ticket, the ticket went to the owner of the deployment surface, and the
reference was corrected there, not in the place that found it. Second, it records the failure
mode honestly: a sentence that was true when written, stale a season
later, with no check to catch it. The parity thinking from the
self-hosting chapter applies to documents too — a claim nobody re-checks
is folklore, however it reads.
