The laptop is usually treated as a developer convenience, a
smaller and vaguer copy of the real system. That is backwards. If an
application cannot run on your own computer, it is hard to trust, hard to
debug and hard to hand to anyone else. So the first deployment of anything
built on digithings is the computer in front of you.

## The first hour

Start the local stack, load the seed documents with one command and ask the
chat a question. They answer straight away, so the first thing you see is the whole loop working: the
interface, the hub, a model and a trace of what happened. Then connect the
model you actually want, local or hosted, and ask again.

## The first week

Pick the one use case closest to your work and switch on only what it needs.
For research, that is the research vertical and retrieval over your own
notes. For documents, retrieval and the vault. For an agent, the tools you
already have, described over MCP so the hub can call them. Keep the trace on
and read it. It shows how the system reached each answer, which is the
fastest way to learn where to change it.

## When it outgrows the machine

You will know, because the trace and the machine both tell you: a pipeline that needs more
memory, an index that has grown past the disk, more people than one machine
should serve. At that point, move the module that is under pressure, not the
whole stack. Put it on a server you own or in a cloud account, point its
neighbours at the new address and carry on. Its tools, its settings and its credentials work there unchanged.

Location is a decision you make when you have the evidence for it, not
before. Open source and open protocols keep that decision yours. Capability
and cost go up only as fast as the work does.

## Where to go next

The design decisions behind each module, with references into the code, are at
digithings.ai/book. The code is open under the MIT licence, and every module
carries its own architecture notes. Build something on your own machine first.
Then put it where it belongs.
