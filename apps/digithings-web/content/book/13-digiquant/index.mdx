Quantitative research has a failure mode most software does not: results
that look rigorous and are not. A backtest that peeks at the future, steps
run in a convenient order, a number nobody can reproduce. Each one
manufactures confidence. digiquant is built so those outcomes are hard to
produce by accident, because the honest order of operations is the only
order the pipeline will run.

Belief in a digiquant number rests on process. Research moves through fixed
stages, each stage declares what it reads, and every result records the
engine and build that produced it, so it can be checked later.

## How it works

The unit of work is the whole pipeline. A caller asks for a research
task; digiquant plans the stages, runs them through an established
backtesting engine and returns the result with its provenance attached.

```mermaid each arrow is a contract: a stage reads only what the stage before it wrote
flowchart LR
  DATA[data] --> VAL[validate]
  VAL --> BACK[backtest]
  BACK --> OPT[optimise]
  OPT --> EXP[export]
```

That single rule keeps look-ahead bias out: a
strategy only sees what earlier stages wrote. The honesty checks are part of
the pipeline itself. An estimate the checks refuse comes back empty, with no
plausible number to mislead anyone, and a partial result is labelled partial.

## Where it fits

digiquant publishes its tasks as tools, so the hub can ask for research
without knowing how quant work is ordered. Market history comes in from the
data layer; results go out to whoever asked, whether that is the
chat, a scheduled session or a dashboard. Model calls go through the shared
model layer, and every run is traced, so a Sharpe ratio on a
dashboard leads back to the run and engine build behind it.

The pipeline runs wherever compute is cheapest for you: beside the data on
one machine for fast backtests, on a timetable in the cloud, or on hardware
sized to the workload. The ordering rules travel with it,
because they are written into the code itself.
