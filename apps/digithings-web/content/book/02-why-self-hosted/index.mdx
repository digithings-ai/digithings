title: Software that lives anywhere
order: 2
summary: >-
  An AI application should not be tied to the machine it first ran on. Build on a laptop, scale in place, move to the cloud without a rewrite.
---

An AI application should not be tied to the machine it first ran on. Over
its life the model endpoint changes, the data grows and the number of people
using it goes from one to many. The application should not have to change
with them.

An assistant product decides where your software lives on day one: you get an
account, a workspace, and your data lives in their region. An agent framework
built around one vendor's runtime only runs where that runtime runs. A pile of
your own scripts runs exactly where you put it and nowhere else. By the time
you know what the application needs, the choice has been made for you, and
undoing it is a migration project.

digithings takes the opposite position. The same code runs on a laptop, on a
server you own and in a cloud account, with the same service contracts, the
same setting names and the same identity model in each. The cloud home in
production today is Cloudflare, where the same services run in containers
behind its edge. You build locally, prove the application on real data, and
move it when the work needs more capacity.

```mermaid one application, three homes: the contracts between modules are the same in each
flowchart LR
  APP[one application] --> L[your laptop]
  APP --> S[a server you own]
  APP --> C[a cloud account]
```

This is not an argument against the cloud. A cloud account is often the
right home for a production service. The argument is against choosing
infrastructure before you know what the application needs, and against
infrastructure that makes the choice hard to revisit. The price is that you
run the stack yourself: updates, backups and the machine are yours to keep.

Three things keep the choice open. The code is open source, so nothing is
hidden behind an account. The seams between modules are standard protocols,
so any module can run on a different machine from its neighbours. And no
module assumes where the others live: each finds its neighbours through
configuration, never through a hard-coded address.

So location stops being an architectural commitment. Stay on one machine
while the work is small. Move to a cloud account when it needs more capacity.
Put one module on its own hardware when it grows faster than the rest, say an
index that outgrows the laptop's disk. At every step it is the code you
started with.
