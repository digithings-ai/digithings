## 1. The one rule

> **A uuid-shaped `:key` is a document id, never a key.**

One rule, two consequences:

- **Writes.** `upsertIssueDocument` refuses a uuid-shaped key with **409**, the message naming the id-to-key mismatch and `details: { key }`. Nothing is created.
- **Reads.** When the ref parses as a uuid, resolve it by `documents.id` (`eq(issueDocuments.documentId, ref)`) **and by nothing else**.

That is the whole design. No lookup-order rule, no fallback chain, no ambiguity to reason about: a uuid ref has exactly one meaning and a non-uuid ref keeps exactly its old meaning.

## 2. Why the guard is not in `issueDocumentKeySchema`

The CTO's option 1 offered "a uuid rejection in `issueDocumentKeySchema`, **or** 409 in the create path". The schema option is **impossible** without breaking option 2, and the reason is mechanical:

The eleven document routes in `server/src/routes/issues.ts` validate the path segment themselves, before the service is ever called — at 10110, 10156, 10201, 10281, 10319, 10397, 10459, 10625, 10682, 10733, 10770 and 10918, each `issueDocumentKeySchema.safeParse(key)` answered with `res.status(400).json({ error: "Invalid document key", ... })`.

So a schema that rejects uuids makes **every read-by-id a 400** and strands the six orphans exactly as they are today. Requirement 2 exists to make those rows addressable; the schema option removes the only thing that makes them addressable. The 409 in the create path is the option that satisfies both requirements, so that is what the leaves implement. The schema stays exactly as it is.

Two of the pinned tests exist to keep that decision honest: a uuid must still **parse** in `issueDocumentKeySchema`, and the routes keep validating before the service resolves.

## 3. Fault 1 — the documents route has no id fallback

Every lookup in `server/src/services/documents.ts` filters `eq(issueDocuments.key, key)` and nothing else — seven sites, lines 167, 193, 248, 596, 696, 743 and 790. `issueDocumentKeySchema` is `/^[a-z0-9][a-z0-9_-]*$/`, max 64, so a lowercase uuid is a valid key. A write addressed by document id therefore finds no row, takes the create path, and builds a second document whose key **is** the uuid. It answers 201. That shadow row is what every later by-key read and the interaction target validator resolve, which is why they disagree with a read of the uuid row.

The guard at `documents.ts:419-421` only fires when `baseRevisionId` is set, so a create without it sails through.

### What Leaf A does

1. Read paths (`getIssueDocumentByKey`, `listIssueDocumentRevisions`, `restoreIssueDocumentRevision`, `lockIssueDocument`, `unlockIssueDocument`, `deleteIssueDocument`, and the existing lookup inside `upsertIssueDocument`): a uuid-shaped ref resolves by `issueDocuments.documentId`, **never** also by key — matching both would be ambiguous against an existing shadow row.
2. Write path (`upsertIssueDocument`): a uuid-shaped key is refused with 409 before anything is inserted. Content writes must use the real key; the uuid only addresses the row for reads, repair, lock, restore and delete.
3. A key that merely **contains** a uuid substring (`plan-<uuid>`) stays valid. Only a ref that is *entirely* a uuid is an id.

`isUuidLike` already exists — `packages/shared/src/agent-url-key.ts`, exported from `@paperclipai/shared` at `packages/shared/src/index.ts:2537`, already used by `packages/shared/src/validators/search.ts:97,108` — and `server/src/services/documents.ts:5` already imports from that package. No new helper is introduced.

## 4. Fault 2 — `reviewInteractionId` is advertised and never applied

`updateIssueSchema` accepts `reviewInteractionId: z.string().guid().optional()` (`packages/shared/src/validators/issue.ts:891`, next to `reviewRequest`, `reopen`, `resume`, `interrupt`, `deferWakeForGoal`, `hiddenAt`). It has **zero occurrences** in `server/src/services/issues.ts` — no code path persists it. Its only reader is `assertInReviewReviewPath` (`server/src/routes/issues.ts:4440-4520`), which returns `null` early at 4460 and 4462 unless the same PATCH also sets `status: "in_review"` on an issue that is not already there. Only `routes/issues.ts:14183` and `:14564` write the field, and only into activity-log transition details.

So outside a review-entry transition the field is **dropped behind a 200**, with the tell being an empty `changes` map. That is the literal failure the reporter described.

### What Leaf B does

`PATCH /api/issues/{id}` answers **422** when `reviewInteractionId` is present and the request does **not** perform the review-entry transition. The error names the accepted kinds `request_confirmation` and `request_checkbox_confirmation`, and says what is missing.

The condition is on the **transition**, not on the raw field:

```
reviewInteractionId present  AND  NOT (existing.status !== "in_review" && updateFields.status === "in_review")
```

Guarding on `updateFields.status !== "in_review"` alone is not enough: an issue **already** `in_review` can never pass that test, so the field stays silently dropped there. Case 3 of the pinned suite covers exactly that, and a worker who implements the narrower guard fails it. The check sits immediately before the `assertInReviewReviewPath` call at `routes/issues.ts:13922`, as `res.status(422).json({ error: ... })`, matching the existing 422 precedent in the same handler.

**The field is not stripped from `updateIssueSchema`.** It is meaningful during the transition, where `assertInReviewReviewPath` already validates it against a pending non-tool confirmation. No global "empty `changes` means 4xx" rule is added — that would change behaviour for unrelated silent no-ops.

`git grep reviewInteractionId HEAD -- ui cli` returns nothing: no first-party UI or CLI caller sends the field, so the 422 breaks nothing we ship.

## 7. The `baseRevisionId` sub-item — ANSWERED

DIG-2232 left one thing open: the original report says the caller sent `baseRevisionId = 66e4a9ba` and got 201, while that exact combination now returns 409. Either the call predates the guard, or the client dropped or renamed the field.

**The call did not predate the guard.** The guard `throw conflict("Document does not exist yet", { key })` was introduced in **`45998aa9a`** — "feat(issues): add issue documents and inline editing", 2026-03-13, the commit that created the feature. It is present at `8f8a0ab7:420` (the running-bundle baseline) and at `fd8c6b920:420` (fork HEAD), and `git merge-base --is-ancestor 45998aa9a` succeeds for both. There was never a revision of this code in which `{unknown key, baseRevisionId set}` answered 201. **CONFIRMED.**

**So the field never reached the service**, and there is exactly one server-side path to this loss: `baseRevisionId` absent or `null` at `upsertIssueDocument`, which flips an update into a create. Leaf A closes that path by refusing a uuid-shaped key outright, whether or not `baseRevisionId` is set. No second remedy is needed.

Two supporting facts:

- `upsertIssueDocumentSchema.baseRevisionId` is `z.string().guid()`. `66e4a9ba` is eight hex characters and cannot pass that validator — had that literal reached the route body the answer would be **400**, not 201. The value in the report is a truncated prefix of the real revision (`66e4a9ba-…`, "revision 5"), so it is a rendering, not a field value the server ever saw.
- The two PUTs the report calls identical were **not** identical. The 201 left the shadow on DIG-2098 keyed `74ddc294-…` carrying `b7196855` and the 39 850-char body, which can only have come from a PUT to `/documents/74ddc294-d70d-40a2-a17c-519d79f42bc4` — the **id** path. The 200 that produced a real revision 6 came from a PUT to `/documents/design-note` — the **key** path. That path difference *is* Fault 1, and it is why the retry looked like the same request.

**Explicitly carried, and it is not a code change:** the exact mechanism by which the reporting client's `baseRevisionId` was lost (nested under a `document` object, renamed, or simply not sent) is **UNKNOWN**. The server kept no log of that request and the report only preserves a truncated prefix. The caller-side runbook entry already covers it, and the DoD does not require it.
