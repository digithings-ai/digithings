## Goal

`TearsheetData` was designed for the Slappers: round-trip long/short trades, `win_rate_pct`,
`profit_factor`, `overall`/`long`/`short` breakdowns. Publishing an SDCA book through it unchanged
would put **numbers that are technically computed and practically meaningless** on a public site.

A DCA book buys on hundreds of days and may never close a position. Its "win rate" is an artifact of
how the position accounting happens to segment a continuous accumulation; its "profit factor"
likewise. A reader comparing `btc_sdca`'s 100% win rate against `btc_slapper`'s would be reading
noise.

The honest question for a DCA strategy is: **did dollar-cost-averaging on this signal beat just
buying, and beat averaging blindly?** Publish that instead.

## The metrics that matter

| Field | Definition |
|---|---|
| `vs_lump_pct` | final value vs. deploying all capital on day 1 — already computed in `SdcaBacktestReport` |
| `vs_flat_dca_pct` | final value vs. **fixed daily amount over the same window** — the real benchmark, since it isolates the *signal's* contribution from DCA's own averaging effect. New; this is the number that says whether the valuation model earns its keep. |
| `avg_cost_basis` | total spent / total units acquired |
| `final_cost_basis_vs_price` | cost basis as a % of the final price |
| `capital_deployed_pct` | peak and final share of initial capital actually put to work |
| `units_accumulated` | ending position |
| `buy_days` / `sell_days` / `no_trade_days` | already in `SdcaBacktestReport` |
| `avg_risk` / `avg_rate` | ditto |
| `max_drawdown_pct` | keep — meaningful for any book |

`sharpe_ratio`, `sortino_ratio`, `calmar_ratio`, `max_drawdown_pct` and the equity/drawdown curves
stay as they are. **`win_rate_pct`, `profit_factor` and the `long`/`short` breakdowns must be `null`
— not `0`, not omitted — for `kind == "dca"`**, so a renderer or a reader can tell "not applicable"
from "zero". Getting this wrong is the whole point of the issue.

## Scope

1. `TearsheetDcaBreakdown` in `tearsheet_data.py` and an optional `dca: TearsheetDcaBreakdown | None`
   on `TearsheetData`. Schema `1.3`; absent on every existing payload, so old tearsheets stay valid.
2. Flat-DCA benchmark in `sdca/backtest.py`: same window, same starting capital, fixed daily spend,
   so the three curves (SDCA / lump-sum / flat-DCA) are directly comparable. Add it to the per-day
   export frame and to `SdcaBacktestReport`.
3. Populate the block in the SDCA publish path from the **Nautilus run** — `SdcaBacktestReport` is a
   CI-only parity harness and must never become the published number (`digiquant/ARCHITECTURE.md` is
   explicit about this). Derive the DCA metrics from the engine's fills and the mark-to-market equity
   curve; assert parity against the harness in a test rather than substituting one for the other.
4. Mirror the fields into the Supabase index-extras projection so the library card can show
   `vs_lump_pct` where a Slapper card shows win rate.

## Unit conventions — get these right and pin them

`_pct` in this schema is **not** consistent: `total_return_pct` and `vs_lump_pct` are ×100, while
`max_drawdown_pct` is a raw negative fraction ("e.g. -0.15"). #2552 caught exactly this trap, and
#2549 documented it. Every new field here must state its convention in its docstring and be asserted
against a hand-derived value in a test where a 100× error would be visible.

## Acceptance criteria

- [ ] `vs_flat_dca_pct` computed against a fixed-daily-spend benchmark over the identical window,

- [ ] For `kind == "dca"`, `win_rate_pct`/`profit_factor`/`long`/`short` are `null`, and a test

- [ ] The published DCA metrics come from the Nautilus run; a test asserts they match

- [ ] Each new `_pct` field's convention is documented and pinned by a test where a 100× error fails.
- [ ] `pytest -m unit -k "tearsheet or sdca"` passes; `make score` clears all four dimensions.
