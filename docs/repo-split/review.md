# Repo split: critical review of the 8-repo proposal

Reviewer: Claude consultant (Principal Engineer bench), DIG-3518, 2026-10-14.
Reviewed: the verified proposal attached to DIG-3518 (`repo-split.md`, scanned at `develop` 83a104a10)
and the live state of `digithings-ai` on GitHub and Cloudflare at `develop` 58e18e69b.
Scope: repository layout, GitHub org settings, Cloudflare Worker inventory. I did not read
production data, run any deploy, or open the Cloudflare dashboard.

## Verdict: MODIFY

**Agree with the topology** (R0 public + R1–R7 private, the boundaries and the dependency
directions). The proposal's coupling inventory (its §1) is accurate and is the real work.

**Modify the mechanics.** Five of the proposal's assumptions do not hold against the live
org, and two of them would stop the plan partway through:

| # | Proposal assumes | Reality (evidence) | Impact |
|---|---|---|---|
| F1 | Protected release branches and `environment: production` gates in every private repo | Org `digithings-ai` is on **GitHub Free** (`gh api orgs/digithings-ai` → `plan: free`). The existing private `twelve-x` returns *"Upgrade to GitHub Pro or make this repository public"* for both branch protection and rulesets. On Free, private repos also get no environment secrets. On Team, private repos get protection, rulesets, environment secrets and deployment-branch policies, but **not required reviewers or wait timers** (GitHub docs, "Deployments and environments"). | Blocker. Every "protected `release/*` + env gate" in R1–R7 is impossible today. |
| F2 | R1 publishes a Python package to "GitHub Packages (private PyPI index)" | GitHub Packages supports npm, RubyGems, Maven/Gradle, NuGet and containers. **No Python registry** (GitHub docs, "Introduction to GitHub Packages"). | Blocker for R2→R1 as written. |
| F3 | Client files are scrubbed from public history *last*, after all extractions | The repo is **public, MIT**, and its history already contains the paths the proposal moves to R1, R6 and R7. Scrub-last keeps them public for the whole migration (weeks). Dates and the exact path list are on the tracking issue, not here. | Security. Also a licensing fact (L1 below). |
| F4 | Interim npm via GitHub Packages | GitHub Packages npm needs a classic PAT **even to install public packages**. Cloudflare Pages Git builds would need that token. | Avoid the interim; go straight to npmjs or keep source consumption until the cut. |
| F5 | "Cloudflare stops auto-deploying from `main`" covers the problem | Only the two **Pages** projects (digiquant.io, digithings.ai) auto-deploy from `main` (Git integration, per the headers of `deploy-digiquant-cloudflare.yml` / `deploy-digithings-cloudflare.yml`). `digithings-stack` and `digithings-digichat` Workers have **no Workers Builds and no deploy workflow** (Workers Builds API: 0 builds) — they are deployed by hand with `wrangler deploy` from a local tree, as is digichat via `scripts/occ_invite_key_rollout.sh`. | The real risk on the platform side is laptop deploys from an arbitrary tree, not `main`. R5 must add a tag-driven deploy path and retire manual deploys. |

Smaller gaps:

- **G1 Unmapped Cloudflare inventory.** Worker `corpus-index` (created 2026-10-13) has no source directory on `develop` (only references in `digigraph/corpus_routing.py` and tests). `digitrace-langfuse` and `digidata-api` have `wrangler.toml` but are not in the account's Worker list. The migration needs a reconciled inventory: every deployed Worker/Pages project → one repo, one workflow.
- **G2 The path manifest drifts.** `develop` moved 83a104a10 → 58e18e69b on the same day (6,811 → 6,788 files). The per-repo path lists must be generated by a script from a pinned SHA and checked for "every tracked path is assigned exactly once", not hand-maintained.
- **G3 Supabase drift.** R0 shipping a "minimal self-host schema" while R2 owns the 140 production migrations means the open engine's tables have two definitions. See recommendation M7.
- **G4 R6 must not deploy R5.** `occ_invite_key_rollout.sh` runs `wrangler deploy` on the digichat Worker. In R6 it may only write KV, R2 seeds and Worker secrets; the deploy step stays in R5.
- **G5 Dual-home window.** Between "extract with history" and "delete moved paths from public" the same code lives in two repos. Nothing in the proposal stops a PR from landing on the old copy.
- **G6 Actions minutes.** Public repos run Actions free. The monorepo ran 1,000+ workflow runs from 13 Oct 00:00 to 14 Oct ~14:30, ≥2,186 run-minutes (wall clock; billable job-minutes are higher because jobs run in parallel). Every workflow that moves private is billed at $0.006/min (Linux 2-core) beyond the plan's included minutes. Confidence: UNSURE on the monthly total, LIKELY on the order of magnitude (tens of thousands of minutes/month if all CI went private).
- **G7 The repo-split docs themselves are sensitive.** A precise map of where client prompts and strategies sit in public history tells a reader what to fetch before the scrub. This PR therefore commits the plan at directory granularity only; the file:line manifest stays on the issue (DIG-3518 documents) and in the private repos.

## Outcome of the gate decisions (2026-10-14)

Chris answered the gate cards: **stay on GitHub Free** (D-G1 no), **keep the repo public until the
end** (D-G2 no, so M1's day-0 flip is dropped), **fresh public repo** (D-12′, M1's second half kept),
**tags in R0** (D-R3), **self-hosted runners** for private repos (D-G4).

What changes:
- F1 is not solved by an upgrade. The replacement gate is the **deploy runner**: deploy credentials
  live only on a dedicated self-hosted runner, and a job-started hook refuses any job that is not on a
  release tag signed by Chris with a hardware-backed key. Agents can push and tag, but they cannot sign,
  so they cannot deploy. Rulesets stay in code, ready for a later Team upgrade. Details: migration plan P2 step 6.
- F3 is accepted risk until cutover. To keep the window short the cutover (R0 public, mono private)
  moves before the private-repo extractions; mono's deploys switch to the runner gate on cutover day.
- G6 goes away: public repos keep free hosted minutes; private repos use self-hosted runners.

Residual risks Chris accepts with these answers:
1. The paths named on the tracking issue stay publicly fetchable until cutover (P1 + P2, about two weeks).
2. Private repos have no enforced branch protection. A direct push to `main`/`develop` is possible;

3. The deploy gate depends on one host. If it is down, nothing deploys until it is back (fail-closed).
4. Self-hosted runners must never be attached to a public repo (fork-PR code execution). Mono gets a
   runner only after it is private.

Open: D-G5 (where the deploy runner runs) and D-G6 (accept the signed-tag gate).

What this means for the plan:

- **O1 — "Origin primary + public GitHub mirror" is not a supported setup.** Origin cannot host a
  public repo, and it cannot push to GitHub. Two ways out, both need Chris (**D-O1**): (a) R0 stays
  **GitHub-primary** and Origin holds an inbound mirror (supported; recommended); or (b) R0 is
  Origin-primary (private) and **we build** a push mirror on the deploy host, and external GitHub PRs
  are pulled back by hand. (b) makes GitHub a copy that anyone with write access can make diverge.
  **Answered: (a).**
- **O2 — Private repos gain real protection.** Rulesets work on Origin-hosted private repos, which
  GitHub Free could not give us (F1). This only helps if agents push with an identity that is **not**
  a bypass actor (**D-O4**). Today agents act as Chris, so a ruleset that lets Chris bypass lets every agent bypass.
  **Answered: agents keep using Chris's account**, so the rulesets are advisory and D-G6 is the hard control.
- **O3 — The signed-tag deploy gate stays.** Origin has no signed-tag rule, so D-G6 remains the
  only gate that an agent with push access cannot pass. The gate moves from a GitHub runner hook to a
  CI-agent hook on the deploy host.
- **O4 — New CI vendor.** GitHub Actions does not run on Origin pushes. Private repos need Buildkite
  (recommended: native Origin provider, self-hosted agents keep D-G4) or Depot (**D-O3**). **Answered: Buildkite, self-hosted agents.**
- **O5 — A new silent auto-deploy path.** The Cloudflare app for Cursor would auto-deploy Workers on
  push. The plan forbids installing it (P0) and keeps deploys on the signed-tag gate.
- **O6 — Beta risk.** Names are permanent during beta, the API had a breaking change two weeks ago,
  and controls "may expand during early beta". twelve-x is a client repo (**D-O5**). **Answered:** Chris confirms no client contract applies and he
  has full control of the codebase; twelve-x moves to Origin in P4.7 with no extra gate.
- **O7 — GitHub Packages is gone for private repos.** D-Q7 (`@digiquant/contract` from GitHub
  Packages npm) needs a replacement: a git dependency pinned to a tag on Origin.

## Review by dimension

### 1. Repo boundaries, public vs private — agree, with notes

- R1 separate from R2: agree. Strategy access is narrower and a version pin is the cleanest rollback.
- R5 vs R6 separate (D-1): agree. Client-confidential data needs per-client access later; tenant changes must not rebuild containers.
- R4 private (D-W1): agree for now. Note the book's *content* about open modules can be pulled from R0 docs at build time, so R4 stays thin.
- twelve-x desk pages → R7 (D-X1): agree, but do it last among the web moves. The gate/palette hooks (`client-product-gate.tsx`, `command-palette.tsx`) are a refactor in R3, not a move.
- `.claude/ .cursor/ agents/ agents.yml opencode.json projects/` (D-13): these drive the agent fleet today. Do not delete them before Paperclip seat instructions stop reading them. Move to a private `digithings-ops` repo **only if** something still reads them (check with `rg` over `~/paperclip-workspace` and the instance dirs first). This is not a ninth product repo; it is config.
- `packages/design` is public npm while brand assets are private R4 (D-6): check that `design` contains tokens only and no logo/brand files before publishing.

### 2. Dependency directions — agree, two tightenings
The rule holds in the proposal: nothing public depends on private; the only private→private build edge is R2→R1 through a version. Tightenings:
- **Plugin API as a contract (R1→R0).** R1 imports from public `digiquant`. Without a declared surface, any R0 refactor breaks R1 silently. Add a `digiquant.plugin` module (entry-point groups, `Strategy` base, MCP tool registration, CLI registration) with semver guarantees; R0 CI runs a dummy-plugin conformance test; R1 CI runs nightly against `digiquant@main`.
- **Route `/dashboard-api/*` directly, not through R5.** The proposal unfolds dashboard-api into its own Worker (good) but keeps R5's stack Worker routing to it via a service binding. A zone route on `digiquant.io` (or a `dashboard-api.` subdomain) straight to the dashboard-api Worker removes the R5→R2 edge entirely and means an R5 deploy can never take the desk API down. Keep the `RUNNER` binding (cron → runner) — that one is inherent.
- The cron Worker (R5) dispatching R2 and R7 workflows is acceptable runtime coupling, but the job list then lives in R5 while the jobs live elsewhere. Acceptable for now; record it in R5's README as an explicit cross-repo contract.

### 3. CI/CD, protected release branches, stopping auto-deploy from `main`
- *Superseded 2026-10-14: the org stays on Free; the gate is the signed-tag deploy runner (see "Outcome" above). Original analysis kept for the record:* Blocked by F1 until the org is on Team. With Team, the human gate moves from "environment required reviewers" (not available on private Team) to **"`release/*` is protected and requires a CODEOWNERS (Chris) approval"** plus a **deployment-branch policy** so `production` secrets are only readable from `release/*` and release tags. That is equivalent in effect: nothing deploys unless Chris approved the PR into `release/*`.
- **Pages:** switch both projects from Git integration to **direct upload from GitHub Actions** (`wrangler pages deploy` from the deploy runner on a signed `web-v*` tag). Cloudflare does not let you add Git integration to an existing direct-upload project, and moving a Git-connected project to another repo means disconnect/reconnect in the dashboard. Creating a fresh Pages project per site, deploying it from the new repo, and then moving the custom domain gives a cutover whose rollback is "move the domain back". It also removes the need for the Cloudflare GitHub app to read private repos.
- **Workers:** every Worker gets exactly one deploy workflow, triggered by a release tag on its repo, `wrangler deploy` from a clean checkout of that tag on the `[self-hosted, deploy]` runner. Manual `wrangler deploy` is retired: the deploy API token lives only on the deploy runner host.
- **R0 release branches.** The proposal keeps 16 protected `release/<module>` branches in R0 where nothing deploys. Publishing is already driven by tags (`<name>-vX.Y.Z`). Release branches add value only for backports. Recommendation: release-please on `main`, protected tag rulesets (`*-v*` creatable only by the release bot), and `release/<pkg>-X.Y` maintenance branches created on demand. This trims the G07 "per-package release branches" for the public repo only; it needs Chris's yes (decision D-R3).

### 4. Git history preservation and scrubbing
- `git filter-repo` per target from a fresh `--mirror` clone is right. Add: `--paths-from-file` generated by the manifest script (G2), `--path-rename` for the new layout, `--replace-message` for client names, then `gitleaks detect` and a denylist grep over **all** objects (`git rev-list --all --objects`) before the first push.
- **Scrubbing the public repo in place does not remove the data.** GitHub keeps `refs/pull/*/head` for the 30 open PRs and all closed ones; those cannot be force-pushed by us and stay fetchable by SHA until GitHub Support purges them. 478 branches and 45 tags would all need rewriting, and every open PR would be invalidated.
- Existing forks are outside our control; check them against the private-path list before the cut (details on the tracking issue).
- *2026-10-14: Chris kept the fresh repo but declined the day-0 private flip; the rename and flip now happen at cutover (plan P3).* **Recommendation (M1):** do not scrub in place. Rename the current repo to `digithings-mono` and make it **private on day 0**, so exposure ends immediately and PRs, issues and Actions history survive. Create a **new public `digithings-ai/digithings`** (R0) later from a scrubbed, allowlist-filtered export with history. The old name's redirect ends when the new repo is created, which is the intended effect. Cost: 1 star, the fork network (desirable to detach), and Actions minutes while the monorepo is private (G6).

### 5. Secrets, KV, GitHub environments
- Agree with "never in a repo": tenant config to KV `TENANT_CONFIG`, seeds to R2. Deploy keys: on Free, private repos have no environment secrets, so deploy keys live only on the deploy runner host (not in GitHub at all).
- Add: use a **GitHub App** (installed on R2 and R7 only) for cron's workflow dispatch and for R2's read of R1, instead of `GH_DISPATCH_TOKEN`-style PATs. Apps give per-repo scope, short-lived tokens and no person-bound expiry.
- Add: **one Cloudflare API token per repo**, scoped to that repo's Workers/KV/R2/Pages (R6 gets KV+R2 write only, no Workers deploy). Today's account-wide tokens become the rotation target in the cut-over of each repo.
- Add: rotate anything that was ever printed in a public workflow log or committed; `gitleaks` over full history in Phase 0 tells us if that list is non-empty.
- Org-level secrets with a selected-repos list are fine for shared non-deploy values (LLM gateway keys), but deploy credentials stay on the deploy runner host only.

### 6. Licensing
- **L1 (fact, not fixable by scrub):** everything that was in the public MIT repo was published under MIT. Anyone who copied a file while it was public holds it under MIT; scrubbing history stops further spread but does not revoke that grant. CONFIRMED (MIT has no revocation clause; the repo's `LICENSE` is MIT). Practical consequence: plan R1's value on what has not been public (calibrations, new research).
- R1–R7: add a proprietary `LICENSE` ("Copyright © 2026 Digi Ecosystem. All rights reserved.") and `"license": "UNLICENSED"` / `license = {text = "Proprietary"}` in package metadata so nothing is published by accident.
- R3 keeps `LICENSE.luxalgo-vela` / `NOTICE.luxalgo-vela` (Apache-2.0: the NOTICE must travel with the code).
- MIT code moved from R0 into private repos is fine; keep the MIT headers on files that came from outside contributors (DCO).
- Published packages need per-package license metadata (`license = "MIT"` in each `pyproject.toml`, `"license": "MIT"` in each `package.json`) and `docs/LICENSING.md` stays the third-party register for R0.
- `digikey` license-key gating ships in MIT code, so users may remove it. That is a business-model choice (MIT vs a source-available licence such as FSL/BSL for specific modules); raised as D-L1, recommended default is to keep MIT.
- `strategies/pinescript/indicators/*.pine`: provenance UNKNOWN (ports of TradingView built-ins or original). Check before R1 is published anywhere.

### 7. Developer and agent workflow after the split
- A cross-repo change (engine fix + stack bump) becomes: PR in R0 → release tag → Renovate/bot bump PR in R2/R5. For local work, a `dt-dev` script clones all repos side by side and uses `uv` path sources / `npm` workspaces overlay to develop against local R0 without publishing.
- Paperclip: one project per repo (or project-repository bindings), `dt-create-issue --project` mapping, `com.digithings.merge-queue` (today drains only `digithings` and `twelve-x`) extended to all repos, worktree sweep and run-watch pointed at the new repos, DCO app installed on each.
- Seat instructions and skills that hard-code monorepo paths (`apps/...`, `digiquant/...`) must be updated in the same phase as the move; otherwise agents open PRs against dead paths.
- CI cost: keep heavy test matrices in public R0 (free minutes). Private repos run only their own tests plus a nightly "latest R0" compatibility job, on self-hosted `[self-hosted, ci]` runners (D-G4).
- Agents never create release tags; they prepare the release PR and changelog, and Chris signs the tag.
