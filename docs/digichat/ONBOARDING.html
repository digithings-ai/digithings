digichat — a chat product, its skins,
its backend, and how it ships

digichat is a Next.js 16 chat UI plus its own backend-for-frontend. One deployment serves a chat widget you can embed anywhere, and the look is a parameter — a skin — so the same product can render as any of twelve different chat interfaces. Everything below is the map: where the code is, how a message travels, how settings and secrets are handled, and how a release reaches production.

digichat v2.3.2 apps/digichat · Next.js 16 · AI SDK v7 · assistant-ui 12 skins · 1 backend BFF — no upstream key in the browser ghcr.io/digithings-ai/digichat

≈ 8 minute read · every path is relative to the repo root · last verified against develop

01In 60 seconds

If you read nothing else, read this box.

A user opens a page with digichat on it — the marketing site's /chat iframes it, or a customer embeds it directly. The browser loads a React chat UI from apps/digichat. When the user sends a message, the browser POSTs it to digichat's own route handler, POST /api/chat. That route is the BFF: it authenticates the caller, resolves which tenant/config applies, and then calls the real model backend (digigraph, or Azure Foundry) using a credential that never leaves the server. The answer streams back.

Which chat interface you see is chrome.skin — a value in the deployment's config, not a code fork. Twelve skins ship in the image, including the first-party digichat look that the marketing site uses. A local surface (/baseline) mounts all twelve against one backend so you can iterate on any of them in one place.

Inside apps/digichat

Routes — src/app/

  • (digichat)/ — the production surface and its root layout. / routes by config mode; /embed is the iframe surface.
  • (baseline)/ — the dev-only skin gallery at /baseline. Isolated root layout, no product globals. Returns 404 in a production build.
  • api/ — every backend call. chat/, conversations/, byok/, deploy/chrome, embed/tenant-config, health, plan-proof, mcp/oauth/*, plus the dev-only baseline-chat proxy.

Libs — src/lib/

  • deploy-config/ — the Zod schema, the YAML loader, the client projection. The settings engine.
  • request-auth.ts — requireDigiChatAuth(), the BFF gate.
  • digigraph-upstream.ts · digikey-exchange.ts — how the server obtains its upstream credential.
  • ecosystem.ts — endpoint defaults + the isAllowedServiceUrl() SSRF guard.
  • thread-skins.ts — the skin registry.
  • adapters/ — digithings/ (digigraph SSE) and foundry/ (Azure) stream adapters.

03How a message flows

Every surface — embed, app, gallery — converges on one route: POST /api/chat.

Browser
React + assistant-ui Thread
→
AssistantChatTransport
posts to /api/chat
→
BFF route handler
apps/digichat/src/app/api/chat/route.ts
→
digigraph
SSE chat completions

The BFF route is where all the product logic lives, in order:

  1. Authenticate — requireDigiChatAuth() accepts a machine key (digi_live_…) or an Auth.js session, and returns the tenant + user identity.
  2. Resolve the tenant — which deployment config applies to this host (see Configuration).
  3. Rate-limit — per-IP for anonymous embeds, plus a shared BFF limit.
  4. Gate — the free-turn / trial policy for that tenant (ungated, turn_limited, trial_form).
  5. Lock the run — a per-session mutex so two sends can't interleave.
  6. Pick the backend adapter — digithings/stream.ts (digigraph) or foundry/stream.ts (Azure), and stream the answer back as AI-SDK UI chunks.

Getting the upstream credential

This is the part worth understanding, because it is the whole reason a BFF exists here.

DIGIKEY_BFF_TOKEN
server env
→
digikey token exchange
lib/digikey-exchange.ts
→
short-lived JWT
cached in memory
→
Authorization: Bearer …
added to the upstream request only
The secret boundary. The browser never receives a digigraph URL, a digikey token, a provider key, or a machine key. It gets a session cookie and an opaque thread id. Everything sensitive is added to the outbound request inside the route handler — and client-projection.ts exists purely to strip secrets out of any config that is sent to the browser.

The four rules that hold this together

RuleWhere it is enforced
BFF pattern is non-negotiableAll upstream calls go through route handlers. Projection at lib/deploy-config/client-projection.ts.
Auth on every route except healthrequireDigiChatAuth() in lib/request-auth.ts, called from every route that touches tenant data.
SSRF guard on user-supplied URLsisAllowedServiceUrl() in lib/ecosystem.ts; MCP has its own inverse guard.
Machine keys are bcrypt-hashedTable api_keys (key_hash, key_prefix) via Drizzle; raw key shown once at creation.

Source: apps/digichat/AGENTS.md (non-negotiable rules), apps/digichat/ARCHITECTURE.md (full API + security analysis).

How a skin is chosen

  • Explicitly — chrome.skin in the deployment config, or the DIGICHAT_CHROME_SKIN env override.
  • By tenant — first-party hosts and slugs (digithings.ai, occ, digithings-ai) default to digichat via defaultThreadSkinForTenant(); everyone else defaults to base.
  • In the gallery — ?skin= on /baseline.
Where to do UI work. docs/digichat/SKIN-GALLERY.md is the canonical guide: it explains the registry, the selector chrome, how to add a skin, and the five gotchas that make a skin render wrong (the data-thread-skin marker, Tailwind @source, the font variable, the prefs host, the theme attribute). Start there before touching a skin.

05The UI layer

The chat UI is assistant-ui primitives (Thread, Viewport, Composer, Message) wrapped in our own composition. The first-party Thread is one large file — packages/ui/src/components/chat/gallery-thread/thread.aui.tsx — that assembles the whole thing: viewport, welcome, suggestions, scroll-to-bottom, composer, action bars, branch picker, attachments, reasoning and tool-call disclosure.

Stylesheets — who owns what

This is the part that confuses people. There are several sheets; they are layered, not alternatives.

① packages/design/tokens.css
The palette itself: --bg --surface --ink --hair --term-* --accent, dark and light, keyed on [data-theme]. Nothing renders without this.
② packages/ui/styles/web-theme.css
The Tailwind v4 @theme inline bridge: maps those tokens onto utility names (--color-background: var(--bg), --color-card: var(--surface)…). inline is load-bearing — it keeps utilities resolving at the use site so a scoped theme flip works.
③ packages/ui/styles/chat-aui.css
The digichat skin palette. Declares the dark values on .digichat-thread and the light values behind :root[data-theme="light"] .digichat-thread, plus the assistant-ui variable bridge and the thread-list/attachment/tool rhythm.
④ packages/ui/styles/chatbot.css → apps/reference/app/(chatbot)/chatbot/chatbot.css
A 4-line re-export. The real first-party grammar — welcome copy, composer, block caret, markdown, reasoning, tool UI, portal mirrors — scoped to :is(.aui-theme-stage, [data-thread-skin="digichat"]). Source of truth lives in the reference app.
⑤ Component sheets
chat-core.css (transcript, markdown, mermaid) · chat-widgets.css (tool-call + reasoning disclosure) · digichat-boot-loader.css (boot animation) · digichat-launcher.css (corner launcher) · terminal-*.css (CLI) · product-chrome.css (attribution, embed shell, embed caret) · digichat-ui/styles/cursor.css.

The scope marker — the one thing to remember

The entire first-party theme is scoped to the attribute [data-thread-skin="digichat"]. The Thread declares it on its own root, so every mount path — the gallery, the embed shell, the product shell — gets the same theme without each surface remembering to wrap it. If a skin looks unstyled, check that attribute first. 

// packages/ui/src/components/chat/gallery-thread/thread.aui.tsx
<ThreadPrimitive.Root
  className="aui-root aui-thread-root digichat-thread …"
  data-user-align="left"
  data-thread-skin="digichat"   // ← the whole theme hangs off this
>

The visual language

  • Mono everything. Geist Mono for text and UI (--font-geist-mono, loaded per layout).
  • Zero radius. --radius: 0 — the terminal look. The theme flattens any rounded utility inside the skin scope.
  • Block caret. Native caret-shape: block where supported; a painted overlay where it isn't.
  • DotMatrix. The 5×5 cube glyph system (components/chat/DotMatrix.tsx) — every icon in the UI is a dot-matrix state: scroll, send, copy, thinking, example…
  • Boot loader. A cube field sweeps the composer outline, then types the welcome copy.
  • Hairlines. --hair borders, no shadows.

06Configuration — how settings are containerised

One codebase serves many customers. The difference between them is a deployment declaration: a YAML file, Zod-validated, that describes a tenant's chrome, gate, features, models, tools and backend. Nothing is compiled in per customer and nothing lives in a database — it is a file on disk plus an env overlay, read once at process start.

digichat.yaml
or DIGICHAT_EMBED_TENANTS JSON
→
loader (server-only)
Zod validate · fail closed
→
host → deployment
matched per request
→
client projection
strips tokens, URLs, keys
→
browser
chrome + features only

Two shapes, one process

deployment: — single install

One customer, one container. The whole process is the tenant. This is what a self-hoster writes.

hosts: — multi-tenant registry

Many hostnames, one process. A request is matched to a deployment by hostname. This is how digithings serves several sites from one container.

What a deployment declares

# illustrative — the real schema is apps/digichat/src/lib/deploy-config/schema.ts
version: 1
deployment:
  slug: acme
  chrome:
    mode: embed            # app | embed | modal | sidebar
    skin: digichat          # one of the 12 registry ids
    theme: dark
    accent: { color: "#e2708a", foreground: "#08090b" }
    welcome: { title: "Ask about your portfolio" }
    suggestions: ["Summarise today", "Explain this chart"]
  gate: { mode: turn_limited }   # ungated | turn_limited | trial_form
  features: { attachments: true, modelPicker: false, view: balanced }
  models: { default: "deepseek/deepseek-v4-flash", available: ["…"] }
  tools: { catalog: [{ id: digisearch, default: true }] }
  backend: { type: digigraph }   # or foundry

The three gate modes

ModeBehaviour
ungatedNo cap. The visitor talks freely; billing/limits are the operator's problem. Used by the digithings.ai marketing embed.
turn_limitedA few free turns, then the visitor brings their own key (BYOK) in-chat. The default for an unconfigured container.
trial_formA per-IP server-side counter: 3 free turns, then a form unlocks a longer allowance. The DataTap-style trial.
Tenant identity is the hostname, and it is only for selection. The X-Embed-Host header (or the referer) picks which config applies. Authorization is separate — a tenant token, or a first-party host with an attested first-party origin. Never treat the host header as proof of identity.
Never bake config into the image. Tokens must not be Docker build args — the tenant registry is read from the environment or a mounted file at runtime, so secrets never land in a layer.

07Keys & auth

Two credential classes, plus the upstream exchange. That is the whole model.

Session

An Auth.js encrypted-JWT cookie signed with AUTH_SECRET. Providers: OIDC, a dev password provider, and a production-guarded local bootstrap. This is a person.

Machine key

A digi_live_… key issued by digichat for server-to-server callers. Stored bcrypt-hashed in Postgres (api_keys.key_hash), shown once at creation. This is a service.

Upstream exchange

DIGIKEY_BFF_TOKEN is exchanged server-side for a short-lived JWT, cached in memory, and attached only to the outbound digigraph call. This is our access to the model backend.

What the browser can see: only NEXT_PUBLIC_* variables and the client projection of the config — chrome, features, model ids, tool ids. Never a URL with credentials in it, never a token, never a key. X-Digichat-Session is an opaque thread UUID, not the session token.

08Deployment

digichat ships as a container image. Two profiles cover the two backend stories.

The image

  • apps/digichat/Dockerfile — node:22-alpine, multi-stage, Next.js standalone output, non-root user, listens on 3000.
  • Ships the Drizzle migrations and example configs so a container can migrate and be configured at boot.
  • Published as ghcr.io/digithings-ai/digichat:vX.Y.Z and :latest.
  • Pin the version in production — never :latest.

The two profiles

  • Profile A — digichat + Postgres + digikey + digigraph + digivault + LiteLLM. The full stack, one compose file.
  • Profile B — digichat + Postgres only, talking to Azure Foundry with the host's Azure identity. No provider key in digichat at all.

What a self-hoster does

  1. Pull a pinned image: docker pull ghcr.io/digithings-ai/digichat:v2.3.2
  2. Pick a profile (A or B) and copy its env example.
  3. Fill in AUTH_SECRET, AUTH_URL, the backend credentials (DIGIKEY_BFF_TOKEN for A; Azure identity for B), and the tenant registry with per-tenant tokens.
  4. Bring it up with the provided compose file.
  5. Smoke test /api/health, then open /embed?host=…&token=….

Guides: docs/digichat/INSTALL.md (the client install guide), infra/digichat-release/ (profiles + compose), infra/self-host/compose.ghcr.yml (pull-only full stack), apps/digichat/OPERATIONS.md (operator runbook).

Release automation

  • release-please watches develop (not main) and keeps a single release PR open, accumulating changes. Merging it is a deliberate release decision — not routine hygiene.
  • It targets develop on purpose: a squashed develop → main promotion commit reads as a no-op to a conventional-commits parser and would swallow the changelog signal.
  • Tags are digichat-vX.Y.Z, and the changelog lands in apps/digichat/CHANGELOG.md.
  • Version bump rides the promotion into main; then a release branch is cut from main.

Patching an older release

  • Branch off the previous one so the name equals the version: release/v2.3.3 from release/v2.3.2.
  • Apply the fix, bump, tag, push — a human-pushed tag publishes the image.
  • The fix (never the version bump) is cherry-picked onto develop, or the next promotion clobbers it.
  • Never merge a release branch into main — its version bump would take production backwards.
Two enforcement gaps worth knowing. release/v* has no branch-protection rule yet (the payload exists at scripts/github-rulesets/04-protect-releases.json; applying it is a repo-settings change needing a human). And main requires no approvals — its only required check is Every commit reaching main was reviewed.

Pre-flight before you push

npm run test --workspace digichat
npm run lint --workspace digichat
npm run build --workspace digichat

126 files / 1250 tests pass today. Lint must be zero errors. build also creates .next/standalone, which breaks make doc-check until removed.

The rules you cannot break

RuleWhy
No upstream credential in the browserThe whole BFF exists for this. Route handlers only.
Auth on every API route except healthMulti-tenant data must never be reachable anonymously. The enumerated exceptions are the client-safe projections (deploy/chrome, embed/tenant-config), the OAuth redirect (mcp/oauth/callback), plan-proof, and the dev-only baseline-chat.
SSRF-guard any user-supplied URLEndpoint overrides and MCP servers are visitor-influenced.
Machine keys stay hashedNever log or store raw key material.
Migrations are additiveNew columns nullable or defaulted; never edit a shipped migration.
Read node_modules/next/dist/docs/ before writing Next.js codeThis Next major has breaking changes.
Product names are always lowercasedigichat, never DigiChat — even at the start of a sentence.

How work gets merged

Start with make task ISSUE=N — it reads the issue's component label, routes to the right base branch, and gives you an isolated worktree. Task PRs merge when ready (required CI green, not conflicted, review coverage on the record). Still a human decision: anything into main, release-please PRs, digikey/ auth-crypto, live trading, and new external network exposure.
