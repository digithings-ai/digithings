## Summary

The `digithings-digichat` Cloudflare Container Worker lost its deploy lane on 2026-10-01, when `f54af7052` (#4919, Human Gate) deleted `deploy-digichat-cloudflare-container.yml`. This PR re-derives that lane on `develop` in the shape the repo uses today: a `pull_request` validation job, a pre-approval deploy gate, and a deploy job that runs only on a manual `workflow_dispatch` behind `environment: production`, so only Chris can approve a deploy. Nothing in this PR deploys. The stack lane (`deploy-digithings-stack-cloudflare.yml`) already exists in the current shape since DIG-4612 / #6013 and is deliberately left untouched.

## What this PR delivers

1. **The digichat deploy lane, back.** `.github/workflows/deploy-digichat-cloudflare-container.yml`:
   - `pull_request` → `check`: `npm ci` at the repo root, the digichat image inputs packaged, `npm run typecheck --workspace digichat-cloudflare`, `npm run test --workspace digichat-cloudflare`.
   - `push: main` / `workflow_dispatch` → `check-deploy-gate`: the same validation, on `ref: ${{ inputs.ref || github.sha }}`. It has no `needs`, so the merge path cannot skip the gate.
   - `workflow_dispatch` only → `deploy`: `needs: [check-deploy-gate]`, `environment: production`, the Cloudflare token preflight, then `npm run deploy --workspace digichat-cloudflare`. A merge to `main` validates and deploys nothing.
2. **The image inputs the image needs.** The digichat image bakes `image-packages/digichat/npm/` and six `image-packages/digichat/manifests/*/package.json` files, and `image-packages/` is generated and gitignored. The new composite action packages them (`--npm-only`), re-checks them (`--check-only --npm-only`) and fails the job if any of them is missing or empty.
3. **A pin suite.** `tests/scripts/test_deploy_digichat_cloudflare_container.py` (32 tests) pins the lane's invariants: identical push and `pull_request` path filters, a path filter that covers every tree the image bakes in, the deploy job reachable only by manual dispatch, `environment: production`, a per-run concurrency group, the rev-injecting deploy command, no `working-directory`, a token preflight that never prints the value, and packaging before every deploy.
4. **A gate pin.** Both lanes are now listed in `ENVIRONMENT_GATED`, so a lost `environment:` is visible to the repo's own tests.
5. **Docs and the deploy wrapper comments** that still said the lanes were deleted, or that the digichat Worker has no route to read its id back from. The Worker is routable: `https://digithings.ai/_digichat/meta` answers `200` with `{"containerId":"shared-eef1ee72c20f","rev":"eef1ee72c20f",…}`.

**Two deliberate deviations from the brief, both recorded on DIG-5120:**

- **The deploy command is `npm run deploy --workspace digichat-cloudflare`, not a bare `npx wrangler deploy -c apps/digichat-cloudflare/wrangler.toml`.** The bare form ships the legacy pinned container id (the DIG-3814 / DIG-4487 defect class): the wrapper resolves the commit, deploys with `--var=DIGICHAT_CONTAINER_REV:<sha12>` and reads the id back. The repo's own pins forbid the bare form, and `apps/digichat-cloudflare/scripts/deploy.mjs` says so in its header. The wrapper runs `wrangler` with `cwd = apps/digichat-cloudflare`, so `wrangler.toml` there is used and `image_build_context = "../.."` resolves to the repo root — the same tree the brief asks for, without the `working-directory` the lane forbids.
- **The stack lane is not rewritten.** It is already in the current repo shape since DIG-4612 / #6013. Restating it in the brief's literal two-job shape would drop the image-inputs packaging, the pre-approval gate job and the rev-injecting wrapper: a production regression.

**Two inherited facts, unchanged by this PR:**

- `main` is behind the live digichat Worker script (DIG-2615: main was 1005 behind, 2.3.2 against a live 2.4.0), and the live Worker carries the OCC control and the KV config that `main` does not have. A dispatch at `ref: main` would ship `main`'s tree and could strip the live OCC control. DIG-3390 owns that cutover.
- The `production` environment's branch policy allows `main` deployments only, and this repo's default branch is `develop`. A run started from `develop` is refused by the environment before the deploy job runs, so the lane becomes deployable only once a promotion carries it to `main`. The lane header says so next to the ref input.

## How it fits the project vision

digithings runs its edge on Cloudflare Containers. A Worker with no deploy lane is a Worker that only its author can ship, from a laptop, by hand — that is how the live digichat script ended up ahead of `main` in the first place. Giving the Worker a lane, with the approval gate on the production environment and the deploy behind the same rev-injecting wrapper the local path uses, brings the edge back under the same rules as the rest of the repo: a merge to `main` is validated by CI and deploys nothing, and a deploy is a deliberate, reviewed action.
