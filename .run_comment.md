## Summary
The merge queue reads a verdict out of a posted marker, but nothing emitted one: the third-party code-review skill that writes the marker never carried a `verdict=` field and never submitted a review, so a tool review left the gate blind (2026-10-07, digithings-ai/twelve-x#347). This adds a first-party producer that posts the marker and submits the blocking review in the same run.

## What this PR delivers
`post_review_verdict.py --repo owner/name --pr N --head-sha <40-char-sha> --verdict changes_requested|approved`. It posts the marker as a bare line in a comment of its own (a fenced copy posts a live verdict) and submits the same verdict as a `REQUEST_CHANGES` review. It refuses a short head sha, is idempotent per head, never patches another login's comment, never stacks reviews, falls back to `event=COMMENT` when the login authored the PR, and never submits an approving review. The `/review` command posts the verdict (step 5); the policy doc names the producer.

## Feature or epic it belongs to
DIG-2281 — the marker producer for the merge-queue verdict gate. The consumer side, `scripts/merge_queue.py`, is already live on develop.

## How it fits the project vision
The merge queue decides on machine-readable evidence, not prose. This closes the last gap: a verdict a tool finds has to reach the gate as a marker and as a review state, so "changes requested" stops being a comment the queue cannot see.
